## 1. 目标与决策摘要

将 SKP-PRTS 从现有 Material 风格管理器，重构为具有《明日方舟》莱茵实验终端视觉语言的原生 Android 工具。重点是排版、空间、材质和连续动效的整体质量，而不是简单换色或增加故障滤镜。

采用以下技术路线：

- Compose 承担完整业务界面、导航、输入、确认和无障碍语义。
- Compose Canvas、绘制层与动画 API 承担文字滚动、遮罩揭示、线框和路径动画。
- Android 13 及以上通过 AGSL 增强局部扰动等效果；旧系统保留无需 AGSL 的基础实现。
- 对确实需要实时折射与空间运动的重点场景，验证本地 Three.js 渲染层。它不持有 Root 能力，也不成为应用可操作的前提。
- 保持现有业务调用与 Native 协议，重构展示而不重构 Root 内核能力。

### 1.1 如何理解“1:1 复刻”

| 维度 | 目标 | 不作出的承诺 |
| --- | --- | --- |
| 文字、遮罩、路径、闪切 | 固定参考版本，提取关键帧、缓动和时序，逐项对照 | 不用随机乱码代替参考的完整动效 |
| 材质与三维运动 | 对照模型比例、相机、光照、透射和运动轨迹 | 不承诺不同 GPU、WebView 和系统上逐像素一致 |
| 布局 | 保留视觉秩序，为手机竖屏重新组织信息 | 不把桌面画面等比缩小后当成移动端成品 |
| 内容与身份 | 使用 SKP-PRTS 品牌及真实业务状态 | 不照搬虚构认证结果、档案内容或未经确认授权的素材 |
| 使用体验 | 常用操作直接可达，动效可中断且不改变结果 | 不让每次使用都等待完整开场 |

优先级：业务正确性与可用性 > 交互连续性与可读性 > 核心视觉还原 > 高成本材质增强。降低画质时优先降低像素、阴影和后处理成本，尽量保留运动节奏。

## 4. 视觉规范初稿

### 4.1 整体方向

采用“实验终端”的视觉体系，以 SKP-PRTS 为首屏身份标识。优先冷白、石墨黑、明确的分隔和少量信号色，不混搭多个阵营的标志与装饰体系。

| Token 角色 | 浅色初值 | 深色初值 | 用途 |
| --- | --- | --- | --- |
| 主背景 | `#F4F6F5` | `#111513` | 全屏底色 |
| 表面 | `#FFFFFF` | `#1C211E` | 必要的工具与弹窗表面 |
| 主文字 | `#161C19` | `#EDF2EE` | 内容与关键状态 |
| 次文字 | `#526057` | `#AEBAB2` | 辅助信息 |
| 强调色 | `#E9C84A` | `#E9C84A` | 选中、焦点和少量识别标记 |
| 正常状态 | `#16705B` | `#69C9A7` | 正常、已完成 |
| 错误状态 | `#B83240` | `#FF8791` | 失败和危险操作 |

这些颜色是待截图确认的设计初值，不构成已通过的对比度结论。黄色不直接用于白底小字；所有状态同时使用文字或图标，不单靠颜色区分。

### 4.2 排版与组件

- 中文采用清晰的无衬线字体；数字、版本和命令可采用适当的等宽样式。字体授权、字重和体积在 P1 确认，不直接打包参考项目全部网页字体。
- 建议起点：正文 14-16sp，辅助信息 12sp，页面标题 24-28sp；支持系统字体缩放，不按屏幕宽度缩放字号，不使用负字距。
- 网格以 4dp 为基础，页面常规边距 16-24dp。分组采用全宽区域和细分隔线，不使用层层嵌套卡片。
- 控件以直角、小圆角或必要切角为主；重复条目和弹窗圆角不超过 8dp。触控目标至少 48dp，视觉线条纤细不代表缩小点击区域。
- 工具按钮优先使用现有 Material 图标库，提供明确内容描述及必要提示；模式用分段选择，布尔项用开关，数值用输入或滑杆。
- 主要导航保留四个稳定目的地。紧凑屏幕使用底部导航，宽屏使用侧栏；标题、图标与当前选中状态始终明确。
- 只在有实际空间作用的地方使用玻璃与三维，不为每个设置项增加透明背景和持续动画。

## 6. 动效系统

### 6.1 组件与时序

组件名称为规划名称，可结合现有代码调整。除“参考值”明确说明外，时长均为样板阶段的建议初值。

| 组件 | 机制 | 建议初值/参考值 | 约束 |
| --- | --- | --- | --- |
| `TerminalBootSequence` | 逐字接入、标识路径、局部闪切、进入主界面 | 日常进入不额外等待；重播版单独编排 | 可跳过；不伪造 Root 认证结果 |
| `GlitchText` | 少量确定性片段位移与局部遮罩 | 120-220ms | 只用于标题或短状态，不持续高频闪烁 |
| `RollingText` / `RollingNumber` | 固定裁切窗口内的字形滚动 | 参考值 460ms；日常状态初值 240-360ms | 中途更新衔接最新目标；静态语义保持正确 |
| `RedactionReveal` | 根据实际换行布局绘制遮挡条并依次退开 | 参考完整进度约 0.95s；工具界面初值 240-420ms | 不改写原始文本，不作为保密措施 |
| `TraceIndicator` | 线框、路径与刻度的进度绘制 | 180-320ms | 未知进度不用虚构百分比 |
| `TerminalTransition` | 遮罩、轻位移与有限错峰 | 进入 220-300ms，退出 160-220ms | 可打断，不等待动画后才响应输入 |
| `CoreScene` | 相机、玻璃清晰度、核心结构的状态过渡 | 重点展开 500-900ms | 只用于选定重点场景，不能阻塞操作 |

### 6.2 实现规则

- 使用统一的时间与缓动配置，区分持续空间运动和离散闪切，不把参考 25fps 的帧点解释为应用只能以 25fps 渲染。
- 文字布局与字形测量按内容、字号和约束缓存；能在绘制层更新的属性不驱动整个页面每帧重组。
- 字形按可见字符簇处理，覆盖中文、英文、组合字符与 emoji。优先使用现有排版能力，不按 UTF-16 单个代码单元强行切割文字。
- 可复现的效果使用固定输入或种子，支持测试时冻结时间与定位关键进度；逐帧随机数不能影响业务或布局。
- 输入框、日志正文、包名和危险操作说明不做乱码替换；装饰层不拦截触摸，也不重复进入读屏树。
- 页面切换、搜索更新、关闭弹窗时取消旧视觉任务；不能因重组重新发送安装、授权或重启请求。
- 效果启停同时受当前页面、生命周期、系统动画设置和用户“减少动态”偏好约束。暂停后不得补播积累的闪切。
- 音效与触感只作为可关闭的补充，音效默认关闭；第一阶段不加入背景音乐。不得直接复用参考中的原片短音。

## 7. 技术架构与三维验证

### 7.1 责任划分

```text
Native / AIDL / SDK / Repositories
                 |
        existing ViewModels
                 |
       Compose screens + shell
          |              |
   motion components     | sanitized visual state
                         v
                local Three.js renderer
```

- `ui/theme`：颜色、字形、形状与语义 Token。
- `ui/components`：统一的导航、条目、表单、进度、弹窗和终端文本容器。
- `ui/motion`：可复用动效与生命周期控制，仅在能消除实际重复时增加抽象。
- `ui/scene`：可选的 Android 三维容器、视觉状态映射和失败回退。
- 业务 ViewModel 不依赖动画完成回调判断操作成败。确有展示状态需要新增时，明确区分业务状态与临时视觉状态。
- 不把 Root、授权和模块列表搬进网页，不为纯 UI 重构重建整个应用架构。

### 7.2 Three.js 可行性验证必须回答的问题

1. 在目标 Android WebView 中，WebGL 能否初始化并稳定恢复，是否存在黑屏、透明合成或上下文丢失问题？
2. 一份具有代表性的模型、相机与玻璃材质，能否在手机上达到认可的视觉质量和连续交互性能？
3. Compose 覆盖层、系统栏、手势返回、横竖屏和前后台切换是否正常？
4. 完整断网、资源损坏、渲染初始化失败或质量切换时，原生操作是否仍可立即使用？
5. 阴影、透射、环境遮蔽和景深分别占用多少帧时间、内存与包体，哪些必须保留？

通过后再让首页样板依赖这条视觉路线。未通过时保留已完成的原生动效，记录具体失败设备与效果差异，提交二维/预渲染降级方案供确认；不得以普通模糊替代真实折射后仍声称完成 1:1。

### 7.3 渲染层边界

- HTML、脚本、字体和模型随应用本地打包，固定依赖版本与资源摘要。拟采用受限的本地 HTTPS 资源加载方式，具体实现和依赖在验证阶段确认。
- 禁止远程导航、远程脚本和任意文件访问；资源请求采用明确白名单。此限制只针对新视觉容器，不擅自改变现有模块 WebUI 行为。
- 不向渲染层传递 Root Key、命令、原始日志、应用包列表或任意执行接口。只传递明确的视觉枚举与必要的非敏感数值。
- 不暴露通用 `addJavascriptInterface` 业务桥。需要就绪/失败消息时，仅接受固定类型的渲染状态，并校验来源与会话。
- 使用 Compose 承担点击、确认和无障碍；即使三维层完全不可用，主页面功能仍完整。
- 静止后停止不必要的连续渲染；页面不可见、后台或退出时停止帧循环并按生命周期释放资源。处理 WebView 渲染进程退出和 WebGL 上下文丢失。

## 9. 兼容、质量与性能目标

### 9.1 体验预设与独立设置

提供以下三种易选的体验预设。内部将三维画质与“减少动态”分别保存，用户也可独立开启减少动态。

| 档位 | 内容 | 适用与回退 |
| --- | --- | --- |
| 完整 | 全部二维动效、经验证的三维材质、有限后处理 | 目标设备实测通过后开放；不等于默认采用参考桌面最高画质 |
| 均衡 | 保留核心运动，降低三维分辨率、阴影和后处理成本 | 默认起点；初始化失败则回退到原生视觉 |
| 减少动态 | 稳定状态、短淡入或直接切换，停用故障闪切与持续三维运动 | 用户显式选择或系统关闭动画时优先采用；业务能力完整 |

画质与减少动态是两个概念：降低材质开销不应自动取消所有动画；减少动态必须真正减少运动。保存用户选择，自动降级时说明当前状态，不悄悄覆盖其偏好。

### 9.2 系统与屏幕矩阵

- API 26-32：原生基础动效可用，不调用 AGSL；三维能力另按 WebView 与实际 GPU 验证。
- API 33 及以上：测试 Shader 增强与主动禁用后的回退路径，不以 API 版本直接推断性能。
- 紧凑竖屏至少覆盖 360dp、412dp 宽；同时覆盖横屏、600dp 及以上宽屏、显示缩放、1.0/1.3/2.0 字体缩放与输入法弹出。
- 设备至少包含一台中端真机和一台高刷真机，并记录 SoC、系统、WebView、刷新率、分辨率与测试包摘要。只有模拟器结果不能宣布材质或帧率验收通过。

### 9.3 首轮验收目标

下列指标在 P0 建立旧版基线，在 P2/P3 使用相同设备和脚本比较。可根据测量修订，但必须留下原因，不得事后无记录降低门槛。

| 项目 | 目标与测量方式 |
| --- | --- |
| 输入响应 | 目标：输入到首个可见反馈的 p95 不超过 100ms；不包含业务完成时间。用时间戳与 trace 检查，不等待完整动效才响应 |
| 常规交互 | 在锁定的 60Hz 条件下，目标帧耗时 p95 不超过 16.7ms；同时记录超过实际帧截止时间的比例，目标低于 5% |
| 高刷 | 90/120Hz 分别按实际帧预算检查；未达标不宣称全程高刷，也不靠虚报刷新率验收 |
| 启动 | 不增加强制开场等待；分别记录首帧、首个可操作界面和三维就绪时间。三维未就绪不能阻塞常用操作 |
| 静止/后台 | 无无意义的持续重组与渲染循环；后台返回不会重复启动业务动作或积累动画 |
| 稳定性 | 连续导航、详情进出与旋转至少 30 次后资源能回收；持续交互 10 分钟记录温升、帧耗时、PSS 和 GPU 内存可用指标 |
| 包体与内存 | P0 记录旧版基线，P2 根据代表性场景测量并冻结新增预算；分项记录字体、模型、脚本、纹理和峰值内存，不凭桌面效果无上限添加资源 |

性能验收使用一致的构建类型，优先 release-like/profileable 测试包，调试包只做开发观察。记录预热条件、次数与原始结果；运行至少 5 次报告分布，不以单次最佳值代表性能。
